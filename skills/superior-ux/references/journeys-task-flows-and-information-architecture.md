# Journeys, Task Flows, and Information Architecture

## Start with evidence

Use existing routes, screens, product language, analytics, research, support themes, requirements, and runtime behavior before proposing a new structure. Record assumptions separately. A plausible persona or journey is not evidence that real users behave that way.

## Map only what affects the outcome

For each representative journey, capture:

- user and job;
- context and entry point;
- information or prerequisites already available;
- decisions and actions in order;
- system responses and state changes;
- alternate, interruption, and recovery paths;
- completion signal and useful next step.

Use a flow diagram or numbered sequence only when it makes branches and dependencies clearer. Do not create ceremonial journey maps with invented emotions, quotes, or metrics.

## Design task flows

- Give each step one understandable purpose.
- Put prerequisite decisions before dependent details.
- Delay optional configuration until it helps the current decision.
- Keep destructive, paid, public, or permission-changing consequences visible before commitment.
- Preserve context when handing off between routes, devices, services, or roles.
- Define re-entry after refresh, timeout, sign-in, interruption, or an external redirect.
- Avoid duplicate paths that perform the same job with different terminology or rules.

## Structure information around decisions

Group and label information according to what users need to understand or decide, not the owning team, database table, or internal process. Use stable nouns for destinations and clear verbs for actions. Make current location, available scope, and the path back apparent.

Progressive disclosure should reduce irrelevant choice while keeping essential information discoverable before it affects consent, cost, security, or irreversible outcomes. Deep navigation is acceptable when categories remain predictable; a shallow structure is not automatically simpler.

## Test the model

Walk the structure with realistic goals and content extremes. Look for ambiguous entry points, missing prerequisites, premature decisions, duplicated concepts, hidden consequences, dead ends, and flows that cannot resume. If evidence is weak, label the proposed structure as a hypothesis and state what would validate it.
